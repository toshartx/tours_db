# Функциональные требования к проекту «Киберспортивный портал»

## 1. Аутентификация и авторизация пользователя

Система должна обеспечивать безопасный вход и регистрацию пользователей.

- Регистрация нового пользователя по email.
- Вход в систему по логину (username или email) и паролю.
- Хранение пароля только в виде хэша (argon2id / bcrypt).
- Подтверждение email после регистрации.
- Восстановление пароля через email.
- Завершение сессии (logout) с инвалидацией токена.
- Ограничение частоты неудачных попыток входа (rate limiting).
- Блокировка учётной записи администратором.

## 2. Управление пользователями (CRUD)

Система должна предоставлять администратору полный набор операций над учётными записями.

- **Create** — создание пользователя администратором с назначением роли.
- **Read** — просмотр списка пользователей; просмотр профиля конкретного пользователя.
- **Update** — редактирование данных пользователя (email, username, роль, статус).
- **Delete** — логическое удаление пользователя (`deleted_at`) с сохранением истории.
- Блокировка и разблокировка учётной записи (`is_active`).
- Сброс пароля пользователя администратором.
- Поиск и фильтрация пользователей по роли, статусу, дате регистрации.

## 3. Система ролей

Система должна поддерживать ролевую модель доступа (RBAC).

Предопределённые роли:

- **Игрок** — базовые возможности участия в портале.
- **Капитан** — управление составом команды и матчами.
- **Судья** — рассмотрение тикетов и утверждение результатов матчей.
- **Организатор / Администратор** — управление турнирами и назначение судей.

- Один пользователь может иметь несколько ролей (M2M через `user_roles`).
- Назначение и снятие ролей доступно администратору.
- Проверка прав на уровне API и БД.

## 4. Возможности роли `игрок`

Для авторизованного пользователя с ролью `игрок` должна быть возможность:

- создать команду (становится капитаном);
- отправить заявку на вступление в команду;
- выйти из команды;
- просматривать информацию про игроков, команды, турниры и конкретные матчи;
- отправлять жалобы (тикеты) на рассмотрение судьям.

## 5. Возможности роли `капитан`

Для авторизованного пользователя с ролью `капитан` должна быть возможность:

- добавить игрока путём принятия заявки;
- удалить игрока из команды;
- управлять состоянием матча — отправлять счёт в раундах на подтверждение судье.

> Все остальные возможности капитан наследует от игрока.

## 6. Возможности роли `судья`

Для авторизованного пользователя с ролью `судья` должна быть возможность:

- просматривать тикеты, оставленные игроками;
- блокировать доступ к участию в турнирах игрокам на основании тикета;
- утверждать результаты матча, оставленные капитаном одной из команд.

> Все остальные возможности судья наследует от игрока.

## 7. Возможности роли `организатор/администратор`

Для авторизованного пользователя с ролью `организатор/администратор` должна быть возможность:

- создавать и управлять турнирами (аналогично судье);
- назначать судей;
- управлять пользователями и ролями;
- просматривать журнал аудита.

> Все остальные возможности организатор наследует от игрока.

## 8. Управление командами и составами

Система должна позволять капитану управлять своей командой.

- Создание команды (пользователь становится капитаном).
- Редактирование профиля команды (название, тег, лого).
- Просмотр списка заявок на вступление.
- Принятие или отклонение заявки.
- Добавление и удаление игроков из состава.
- Назначение ролей в составе (captain, player, coach).
- Фиксация истории состава (`joined_at`, `left_at`).
- Роспуск команды (`disbanded_at`).

## 9. Управление турнирами

Система должна позволять организатору создавать и вести турниры.

- Создание турнира: название, описание, формат, даты, `max_teams`, призовой фонд.
- Открытие и закрытие регистрации команд.
- Регистрация команды на турнир (с проверкой лимита `max_teams` в транзакции).
- Генерация сетки плей-офф или расписания round robin.
- Автоматическое продвижение победителя в следующий раунд (`next_match_id`).
- Изменение статуса турнира: `draft → registration → ongoing → finished` (или `cancelled`).
- Просмотр списка участников и таблицы лидеров.

## 10. Управление матчами и судейство

Система должна позволять капитанам и судьям вести матчи.

- Создание матча вручную или автоматически при генерации сетки.
- Назначение даты и времени (`scheduled_at`).
- Ввод счёта по раундам капитаном (`match_games`).
- Отправка результата на подтверждение судье (`matches.status = 'pending_review'`).
- Утверждение или отклонение результата судьёй.
- Автоматическое определение победителя (`winner_id`) по счёту.
- Смена статуса матча: `scheduled → live → pending_review → finished` (или `cancelled`).
- Отмена матча с указанием причины.

## 11. Система тикетов (жалоб)

Система должна обеспечивать обработку жалоб от игроков.

- Подача тикета игроком с указанием категории (`cheating`, `conduct`, `bug`, `other`).
- Привязка тикета к сущности (`player`, `team`, `match`, `tournament`) через `entity_type` + `entity_id`.
- Просмотр списка тикетов судьями с фильтрами по статусу, категории, приоритету.
- Назначение тикета конкретному судье (`assigned_to`).
- Изменение статуса тикета: `open → in_progress → resolved` (или `rejected`).
- Блокировка игрока от участия в турнирах на основании тикета (`players.is_banned`).
- Фиксация решения судьи с временной меткой (`resolved_at`).

## 12. Просмотр турниров, команд и игроков

Система должна отображать актуальную информацию о турнирах, командах и игроках.

- Список турниров с фильтрами по статусу и датам.
- Карточка турнира: описание, формат, призовой фонд, расписание, сетка.
- Таблица лидеров турнира: команды, победы/поражения, разница.
- Список команд с поиском по названию и тегу.
- Карточка команды: состав, история, участие в турнирах.
- Карточка игрока: ник, страна, текущая и прошлые команды, статистика.
- Карточка матча: команды, счёт, формат, дата, статус, результат по картам.

## 13. Журналирование действий пользователя

Система должна вести аудит действий для безопасности и разбора инцидентов.

- Фиксация событий: вход/выход, создание/изменение/удаление сущностей, смена статуса матча, изменение ролей, действия по тикетам.
- Хранение в логе: ID пользователя, тип действия, объект (тип + ID), временная метка, IP-адрес, результат, снимок «до» и «после» (JSONB).
- Хранение попыток входа отдельно (`login_attempts`) с ретеншном 30–90 дней.
- Просмотр журнала администратором с фильтрами по пользователю, типу действия, дате.
- Защита логов от изменения: только INSERT, без UPDATE/DELETE на уровне прав БД.
